Lesson 02 · OWASP LLM10: access controls

Backstage Pass

Per-key model allowlists. Two app keys that differ by a single line: one can reach every model on the gateway, the other only the model its app needs.

The threat

A key that opens every door is worth more to an attacker than it needs to be. If a chat app's key leaks and it can also call every other model on the gateway, the damage is everything the gateway can do.

The control

Least privilege: each credential gets only the access its job needs. On a LiteLLM virtual key that's the models list. Like a backstage pass, it gets you exactly where it says, and a request for any model not on the list is refused at the gateway.

OWASP has no separate Top 10 item for over-privileged keys. This is one of the mitigations listed under LLM10: Unbounded Consumption: "Implement strong access controls, including role-based access control (RBAC) and the principle of least privilege."

The models in this lab

The gateway serves two model aliases. A chat app needs only the first.

qwen    chat (qwen2.5:7b)                 what a chat app needs
embed   embeddings (nomic-embed-text)    turns text into numbers for document search

The Red Team key is created without a models list, and LiteLLM treats that as "every model on the gateway". The Blue Team key lists only qwen.

Watch it run

exercises\02-backstage-pass\run.ps1
==============================================================================
  02 - Backstage Pass   OWASP LLM10: Unbounded Consumption (access controls)
==============================================================================
 
 BASELINE   qwen-only key uses its allowed model
 
   request   POST /v1/chat/completions  (model=qwen, max_tokens=10)
   prompt    "Who is the robot or AI in the film '2001: A Space Odyssey'? Reply with the name only."
 
     OK         2.1s  2001: A Space Odyssey  -> HAL 9000     
 
 RED TEAM   an app key with no model allowlist tries the embed model
 
   key       sk-lC****************ehVw
   made by   Invoke-RestMethod http://127.0.0.1:4000/key/generate -Method Post -Headers @{ Authorization = "Bearer <master key>" } -ContentType 'application/json' -Body '{"key_alias":"ex02-open-224826"}'
   limits    none set - LiteLLM lets the key call every model
   request   POST /v1/embeddings  (model=embed)
   input     "hello world"
 
   result    OK - embedding returned (768 numbers)
 
 BLUE TEAM   the same kind of key, with models=["qwen"], tries the embed model
 
   key       sk-Ds****************oHMQ
   made by   Invoke-RestMethod http://127.0.0.1:4000/key/generate -Method Post -Headers @{ Authorization = "Bearer <master key>" } -ContentType 'application/json' -Body '{"key_alias":"ex02-pass-224827","models":["qwen"]}'
   limits    models=qwen only - no embed
   request   POST /v1/embeddings  (model=embed)
   input     "hello world"
 
   result    BLOCKED 403 The requested model 'embed' is not available for this API key, or the model name is invalid. Check the models available to you and try again.
 
 RESULTS 
 
   Baseline  qwen-only key called qwen - OK
   Red Team  key with no models list reached embed
   Blue Team qwen-only key refused embed with 403
 
 PASS   key restricted to its allowed models

Recorded on a CPU-only Windows PC: Ollama behind a LiteLLM gateway. Compare the two made by lines: the only difference is "models":["qwen"].

What we measured

  • The default is open. Nobody granted the first key access to embed, and nobody took it away either. Leaving out the models list is the easy mistake, and it fails open.
  • 403, not 401. 401 means "I don't know who you are". 403 means "I know who you are, and you're not allowed this". The key was valid, just not permitted for embed.
  • Aliases make it maintainable. Callers ask for embed, not ollama/nomic-embed-text, so the real model behind an alias can change without rewriting any keys.

Limits of the fix

Whatever issues keys (a script, a portal, a person) has to set the list every time, because a key without one gets everything. And an allowlist says which models, not how much: pair it with rate limits and budgets.
